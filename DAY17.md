# Day 17 & 18: Provider Failover & Idempotency

Today's focus was entirely on system resilience against upstream outages, transforming our API Gateway from a single point of failure into a self-healing system.

## Day 17: Provider Failover (The Second Kitchen)

### The Problem
Yesterday, we built a Circuit Breaker. If the primary upstream (e.g., OpenAI) goes down, the breaker trips and we instantly reject traffic. However, instantly rejecting traffic still results in a `503 Service Unavailable` for the end-user. We needed a backup plan.

### The Solution: Ordered Upstreams
We restructured the proxy to handle an array of `Upstream` targets, each equipped with its *own* separate Circuit Breaker. 
During a request:
1. The proxy checks `mock-primary`. If its circuit breaker is OPEN, it skips it instantly.
2. It moves to `mock-secondary`. If that breaker is CLOSED, it forwards the request there.
3. The end-user receives a successful `200 OK` response and has no idea that the primary provider was ever down.

**Edge Cases Tested:**
- **Silent Failures Fixed:** If the primary provider returns `500 Internal Server Error`, we now correctly record it as a failure (fixing a bug where HTTP success with a bad status code was treated as a true success).
- **All Providers Down:** If *both* providers are down, the system exhausts both retry loops and finally returns a `503 Service Unavailable`.

## Day 18: Idempotency (Preventing Double-Billing)

### The Problem
When dealing with network timeouts, there's a dangerous ambiguity. If we send a request to a provider and wait 5 seconds without a response, we don't know if the request never reached them, OR if it reached them, they processed it (and billed us for tokens), and the response simply got lost on the way back.
If we automatically retry that request, the provider might process it *again*. We get double-billed, and potentially cause duplicate side-effects.

### The Solution: The Idempotency Key
We injected an `Idempotency-Key` into the request headers. 
1. If the client provides one, we pass it through.
2. If they don't, the proxy generates a cryptographically secure random string (e.g., `req-7a9b...`) at the very beginning of the request lifecycle.
3. **Crucially:** Because we generate it *before* the retry loop, every single retry attempt for that logical request carries the exact same `Idempotency-Key`.

When the upstream provider sees a retry with a key it has already processed, it simply returns the cached response instead of reprocessing the prompt. Double-billing is eliminated!

**Edge Cases Tested:**
- **Client Pass-Through:** Clients passing their own `X-Idempotency-Key` are respected. The gateway doesn't overwrite it.
- **Retry Preservation:** Retries generated by the gateway correctly reuse the injected key across multiple HTTP transport attempts across multiple upstream providers.
