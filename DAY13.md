# Day 13 — Internal gRPC APIs (gRPC vs REST Trade-offs)

**Concept mastered:** Understanding the architectural differences between gRPC and REST, and why hybrid architectures often expose REST/SSE to the public internet while using gRPC for internal service-to-service communication.
**Built:** A Protobuf definition (`proto/router/v1/tenant.proto`), generated gRPC Go stubs using `buf`, built the implementation in `internal/tenant/grpc_server.go`, and wired it in `main.go` to run concurrently on port `:9092`.

---

## 1. The Scenario: Admin Operations
Yesterday, we built a CLI script (`cmd/keygen`) to issue JWTs. But in a real system, a user signs up on a web dashboard, and the backend needs to programmatically issue an API key. 
We need an endpoint that does this: `CreateTenant(tenant_id) -> returns JWT`. 

Where do we put this endpoint?

## 2. The Design Decision: Why gRPC for Internal APIs?

We decided *not* to expose this endpoint on our public REST server (`:8080`). Instead, we spun up a completely separate gRPC server on `:9092`. Here is the exact trade-off breakdown:

### Why REST/SSE for the Public Proxy (`:8080`)?
1. **Ubiquity:** Every browser, language, and tool (like curl or Postman) understands HTTP/JSON.
2. **Streaming:** SSE (Server-Sent Events) is the standard for LLM streaming that plays nicely with proxies, load balancers, and frontend frameworks. 
3. **Human Readable:** When an external developer integrates with our API, seeing a JSON response makes debugging easy.

### Why gRPC for the Internal Admin API (`:9092`)?
If a billing microservice or admin dashboard needs to talk to the Router, it doesn't need ubiquity or human readability. It needs speed and safety.
1. **Strongly Typed Contracts:** With gRPC, you define a `.proto` file. You can't accidentally send a string where an integer is expected. The compiler generates strict stubs for both the client and server.
2. **Performance (Binary Serialization):** JSON is slow. It's just text. Protobuf (what gRPC uses) packs data into raw binary formats. It is vastly smaller over the wire and vastly faster to serialize/deserialize in CPU.
3. **Security (Port Isolation):** By binding the gRPC server to a different port (`:9092`), DevOps can easily configure the VPC/firewall to completely block public internet traffic from hitting the admin API, while leaving `:8080` open to the world.

## 3. Reading the Implementation

1. **`proto/router/v1/tenant.proto`**: 
   The source of truth. We define the `TenantService` with `CreateTenant` and `RevokeTenant` RPCs. Notice the strict schemas (`message CreateTenantRequest`).
2. **Code Generation with `buf`**:
   We used standard `buf` to compile the `.proto` file into Go code, dropping the stubs into `pkg/api/proto/router/v1/`.
3. **`internal/tenant/grpc_server.go`**:
   This implements the interface generated by `buf`. When `CreateTenant` is called, it generates a cryptographically signed JWT for that tenant and returns it.
4. **`main.go`**:
   We explicitly bind the gRPC server to `tcp :9092` and spin it up in a goroutine before the main proxy server starts. We also wired `GracefulStop()` into our SIGTERM handler so the gRPC server shuts down cleanly alongside the HTTP server.

## 4. What to say out loud in 60 seconds

*"I architected a hybrid network topology for the API Gateway. For external client-facing traffic, we expose a standard REST and SSE interface on port 8080, prioritizing browser compatibility and developer experience. However, for internal administrative actions like issuing JWTs, I implemented a gRPC server on an isolated port, 9092. I chose gRPC for internal service-to-service communication because Protobuf's binary serialization is significantly faster than JSON parsing, and the strict, generated contracts prevent structural regressions. The port isolation also guarantees our admin endpoints are hidden from the public internet entirely at the firewall level."*
